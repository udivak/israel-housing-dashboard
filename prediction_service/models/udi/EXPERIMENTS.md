  - `xgb_balanced`    val_mape=0.2015  best_iter=778

- vs `udi/random_forest_v2` (MAPE 0.2061, MAE 292,847, R² 0.801): XGBoost wins on every metric — slightly better MAPE, ~7K lower MAE, +0.014 R². The shared OrdinalEncoder preprocessor makes this a clean head-to-head; categorical handling is identical, so the delta is the booster vs forest itself plus per-tree column subsampling.
- Top feature importances: `lat`, `deal_nature`, `rooms`, `dist_to_kindergarten`, `lon` — geography + structural attributes dominate, matching what RF v2 emphasized.
- Pipeline trick: fit the `ColumnTransformer` once, transform `X_train`/`X_val` to dense matrices, fit each `XGBRegressor` directly with `eval_set=[(X_val_t, y_val_log)]`, then post-hoc wrap winner into `Pipeline([("preprocess", pre), ("model", booster)])`. Avoids xgboost ≥ 2.0 deprecating `model__early_stopping_rounds` as a `pipeline.fit` kwarg, and avoids fitting the preprocessor twice.
- Open follow-ups: `xgboost_v2` to layer on native categorical (`enable_categorical=True`) and skip the OrdinalEncoder; Optuna sweep around `xgb_slow_wide` (deep + low LR is clearly the winning regime here).

## Run 3 Notes

- Candidate validation MAPE / `best_iteration` (early stopping rounds=150, n_estimators=4000, custom MAPE-real-scale eval_metric):
  - `xgb_balanced`     val_mape=0.1953  best_iter=918
  - `xgb_deep`         val_mape=0.1902  best_iter=1068  ← winner
  - `xgb_regularized`  val_mape=0.1927  best_iter=1505
  - `xgb_deep_reg`     val_mape=0.1912  best_iter=922
  - `xgb_mid_reg`      val_mape=0.1966  best_iter=950
- Final test metrics: MAPE 0.2023, MAE 288,396, RMSE 521,761, R² 0.8129, n=5,945.
- vs `udi/xgboost_v1` (test MAPE 0.2047, MAE 285,538, R² 0.8143): MAPE down 0.0024 (~1.2%), R² down a tick (-0.0014), MAE up ~3K. The MAPE win comes from MAPE-aware early stopping picking a different stop point on log-scale predictions; before, RMSE was minimized on `log1p(y)` so early stopping picked best RMSLE iter, not best MAPE iter.
- Top feature importances (raw column names — no `numeric`__/`categorical_`_ prefix now): `lat` 0.089, `rooms` 0.089, `is_residential_near_100m` 0.067, `city` 0.066, `log_dist_to_beach` 0.062. With native categorical on, `city` jumped from 0.030 (v1) to 0.066 (v2), confirming the partition-based split works better than ordinal-pseudo-numeric.
- Three engineering changes that landed:
  1. **Native categorical**: dropped the entire `ColumnTransformer`/`OrdinalEncoder`. `city`/`neighborhood`/`deal_nature` flow as `category` dtype directly into XGBRegressor with `enable_categorical=True`.
  2. **Categorical alignment helper** (`_align_categories`): `data_v2.split` calls `select_features` independently per slice, so `cat.categories` differ between train/val/test (silent correctness bug for native-cat). The helper canonicalises val/test categories to train's; unseen levels become NaN, which `enable_categorical=True` handles via default split direction.
  3. **MAPE-aware early stopping**: replaced `eval_metric="rmse"` (RMSE on `log1p(y)`) with a callable `mape_real_scale(y_true_log, y_pred_log) = MAPE(expm1(...))`. Critical gotcha: in xgboost 3.x the constructor's `early_stopping_rounds` defaults to `maximize=True` for *callable* `eval_metric` (no auto-direction inference), so we wire an explicit `EarlyStopping(rounds=150, maximize=False)` callback per fit. Without it, every candidate stops at `best_iter=0`.
- Dropped features (importance==0.0 in v1): `is_old`, `is_new`, `is_new_project`, `real_price_imputed`. Implemented defensively (only drop if present) since `real_price_imputed` is added by `data_v2.clean()` only when there are NaN target rows to fill.
- Surprises:
  - val<->test gap widened slightly (v1: 0.0110, v2: 0.0121). All five candidates show a similar ~0.012 drift, so this is shared distribution drift between val and test, not candidate-specific overfitting.
  - `xgb_slow_wide` (v1's winner) was deliberately removed; the new `xgb_deep` (max_depth=10, lr=0.03, min_child_weight=3, reg_lambda=2) lands 0.0035 better on val and 0.0024 better on test — depth=12 was indeed too aggressive.

- Surprise: `xgb_deep` `best_iter` jumped from 1068 (v2) to 1391 — added KNN+geo features keep useful gradient information further into training, so early stopping is more patient. No sign of overfitting (val<->test gap shrank).
- Minor noise: `np.nanmean`/`np.nanmedian` emit "All-NaN slice" warnings on KNN queries where every neighbour's `pps` is NaN (rare). The result is correctly NaN for the feature, which XGB's native missing handling consumes — no functional issue.

## Run 6 Notes (MAPE REGRESSION; MAE/RMSE/R² improved)

- Optuna sweep: 60 trials requested, **25 completed**, 0 pruned. Hit `timeout=3600s` (1h) before reaching 60 — each trial = 5-fold CV with feature engineering re-fit per fold (KMeans, GeoKNN BallTree, categorical alignment all built on the in-fold training data only), so a trial costs ~2-3 min on this dataset.
- Best CV MAPE: **0.2061** (mean across 5 folds: [0.2031, 0.1989, 0.2059, 0.2133, 0.2092]).
- Best params: `max_depth=12, learning_rate=0.0121, min_child_weight=4, subsample=0.754, colsample_bytree=0.692, reg_lambda=0.482, reg_alpha=0.0348, gamma=0.00106`. Final fit: `n_estimators=1209` (median of best_iters per fold: [1457, 1093, 1139, 1499, 1209]) on full train+val (53,493 rows × 80 feats).
- Final test metrics: MAPE 0.2015, MAE 278,688, RMSE 504,365, R² 0.8252, n=5,945.
- **vs `udi/xgboost_v3`** (MAPE 0.1985, MAE 282,393, RMSE 509,958, R² 0.8213): MAPE **up 0.0030 (~1.5%)** → fails plan criterion (1) (which allowed only ~0.001 noise band). MAE down 3,705, RMSE down 5,593, R² up 0.0039. The squared-error-optimal box from Optuna gets bigger errors *less often* (lower RMSE) but its smaller errors hurt MAPE more on the long tail of small-priced rows. CV's `mape_real_scale` eval-metric *was* used for early stopping per fold, but the trial-level objective is mean-MAPE which still optimises the average — it's the trial-→-test transfer that's the issue, not the metric.

- **Architecture (the easy part — built per plan, no surprises)**:
  - `NumericTokenizer(n_num=146, d_token=192)` — vectorised as two `nn.Parameter` tensors `(weight, bias) ∈ R^{146×192}`. Forward pass = single broadcast multiply-add, no per-feature `Linear(1, d)` Python loop. `n_num=146` = 74 raw numerics + 72 `_nan` indicators.
  - `CategoricalTokenizer(cat_cardinalities=[59,113,32,65], d_token=192)` — per-cat `nn.Embedding(card+1, d_token)` reusing the slot-0-unknown convention from Plan 2.
  - 3 × pre-norm `TransformerBlock`: `LayerNorm → MultiheadAttention(d=192, n_heads=8, dropout=0.2, batch_first=True) → +skip → LayerNorm → FFN(192 → 384 → 192, GELU, Dropout 0.1) → +skip`. `need_weights=False` in the production forward to enable PyTorch SDPA fast-path; `attention_rollup()` patches in `need_weights=True` only for the diagnostic pass.

- **Why the result is negative — three honest hypotheses**:
  1. **Data slice too small for a transformer.** 47,550 train rows. FT-Transformer is reported in the paper to start outperforming gradient boosting around the **100k+ row** range; sub-50k slices typically favour boosters. ResNet-tabular (nn_v3, MAPE 0.2203) and FT-Transformer (this) both land in the 0.217-0.220 band on this slice — both are already at-or-near the ceiling of what a single deep-learning model can extract here. The booster ceiling is ~0.198 (xgboost_v3); the gap to that is the "deep learning's overhead on small-tabular" cost, not architecture-specific.
  2. **Single seed + no candidate sweep.** Plan 4 explicitly excluded a sweep ("the focus is the architecture lift"), but every prior NN run that benefited from a sweep (nn_v3b → 0.0031 better than nn_v3 with the same architecture) suggests a `nn_v4b` axis sweep over (`d_token`, `n_blocks`, `n_heads`, `attn_dropout`) could plausibly buy 0.002-0.005 — not enough to beat the booster, but might close the gap to nn_v3b.
  3. **CPU forced the schedule shorter.** Plan called for `N_EPOCHS=150`, we ran 60. The cosine tail is essentially flat after epoch 52, so additional epochs likely wouldn't have helped (val_mape oscillation in epochs 53-60 is ±0.003, not a downward trend) — but we lost the option to try a longer warmup (e.g., `WARMUP_EPOCHS=20` over a longer total schedule) which is the standard remediation when the warmup tail still shows train_loss decreasing rapidly, as ours does at epoch 11 (0.34 → 0.31 in one epoch).
- **Device note (the hard part)**: this implementation FORCES CPU. The full chronology of the MPS battle:
  - **Round 1 — published recipe** (`attn_dropout=0.2`, no grad clip): `train_loss=NaN val_mape=NaN` at epoch 10 print. PyTorch issue #96702 documents that `MultiheadAttention` with `dropout > 0` on MPS in train mode can produce NaN gradients via the fused-SDPA backend.
  - **Round 2 — workaround** (`attn_dropout=0.0`, `ffn_dropout=0.2`, `lr=5e-5`, `grad_clip=1.0`): same `train_loss=NaN val_mape=NaN` at epoch 10. The dropout fix wasn't the root cause.
  - **Round 3 — diagnostic** (`_diag_nan.py`, since deleted): same model + data + hyperparams, but standalone 1000-step probe on MPS — **stays clean**, train_loss decreases 1.32 → 0.27 monotonically. Categorical codes are within embedding bounds (max code = card-1 for every column, all <`card+1`); inputs are fully imputed (no NaN reaches the model). So MPS handles the architecture correctly *in isolation*.
  - **Hypothesis (unresolved)**: validation-pass activation pressure. Train batch=512 → val chunk = `batch_size * 4 = 2048`. With seq_len=151, n_heads=8, head_dim=24 → per-block attention activation tensor is `B × H × T × T × float32 = 2048 × 8 × 151 × 151 × 4 bytes ≈ 1.5 GB`. Peak unified-memory footprint observed via `sample(1)` was 19.5 GB on this M-series machine — borderline. MPS doesn't always raise on OOM; it can silently produce NaN downstream.
  - **Resolution**: forced `device = torch.device("cpu")` directly in `nn_v4.train()`, skipping `_safe_device_with_fallback`. CPU's eager attention is numerically deterministic and the result is reproducible. Cost: 4.5 min/epoch instead of an estimated ~85 sec/epoch on MPS, total wall clock 4 hr 33 min. The 2-arg extension to `_safe_device_with_fallback` (added to `_nn_common.py` per Plan 4 §C.0) is **kept** — it remains a forward-compat hook for future multi-input NN models that might successfully use MPS — but is not exercised here.
- **Trainer changes (in `_nn_common.py` — both backward-compatible)**:
  1. `**grad_clip` kwarg** on `PyTorchTrainer.__init_`_ (default `None`). When set, calls `torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=grad_clip)` between `loss.backward()` and `optimizer.step()`. v1/v2/v3/v3b reruns with the default `None` are bit-identical (verified separately — see Backward-Compat Regression Test below).
  2. **Tensor-accumulator running_loss** (replaces per-batch `loss.item()`): `running_loss_t = torch.zeros((), device=self.device)`, then `running_loss_t = running_loss_t + loss.detach() * batch_size`, with a single `.item()` at end of epoch to compute `train_loss`. Numerically identical to the old `running_loss += float(loss.item()) * bs` (no float32 ↔ float64 difference, no associativity drift — `loss.detach() * int * 1 + running_loss_t` is the same FMA pattern as the old code), but eliminates the per-batch GPU→CPU sync that was dominating MPS profile time at 60% (irrelevant on CPU but kept for forward-compat with future MPS use). Verified bit-identical for v1/v2/v3/v3b.
- **Backward-Compat Regression Test**: re-ran v1/v2/v3/v3b after the `_nn_common.py` changes — all four reproduce their leaderboard MAPE bit-identically:

- **Why this run exists**: every leaderboard row before this is a *single-seed* point estimate. The dashboard would have shipped MAPE=0.1972 for `udi/blend_v1` and MAPE=0.1985 for `udi/xgboost_v3` as if they were measured precisely — but the gap (0.0013) is well inside the noise band of a 5,945-row test slice. - **Stage A — `seed` plumbed end-to-end**:
  - `data.load_data(seed: int = 42)` and `data_v2.load_data(seed: int = 42)` now thread the seed into `split(df, seed=seed)`. Default 42 keeps every existing leaderboard row reproducible to within ±5e-4 MAPE.
  - `run.py` calls `data_mod.load_data(seed=args.seed)` wrapped in `try/except TypeError` for backward-compat with any third-party loader that pre-dates the kwarg. So `python3 run.py udi/xgboost_v3 --data v2 --seed 43` actually changes the split now (was no-op before — the seed was only metadata).

- **Stage B.1 — `seed` plumbed through every stochastic pipeline layer**:
  - `xgboost_v3.train(..., seed=42)`: deep-copies `COMMON` per-fit (`common_seeded = {**COMMON, "random_state": int(seed)}`) so `seed=43` doesn't silently mutate the module-level dict for the next seed=42 caller. Also threads `seed` into `_fit_kmeans(seed=seed)` and `_oof_train_knn(seed=seed)`.
  - `nn_v3.train(..., seed=42)`: replaces `gen = set_global_seeds(SEED)` with `set_global_seeds(seed)`; threads into `fit_kmeans(seed=seed)` + `oof_train_knn(seed=seed)` + `TabularPreprocessor(include_categorical=True, seed=seed)`.
  - `blend_v1.train(..., seed=42)`: propagates to both inline base trainings (`xgboost_v3.train(..., seed=seed)` AND `nn_v3.train(..., seed=seed)`).
  - Shared helpers in `_nn_common.py` extended additively: `fit_kmeans(X_train, seed: int = RANDOM_STATE)` → `KMeans(random_state=seed)`; `oof_train_knn(X, y, seed: int = RANDOM_STATE)` → `KFold(random_state=seed)`; `TabularPreprocessor.__init__(include_categorical, seed: int = RANDOM_STATE)` stores `self._seed` and `fit()` uses it for `QuantileTransformer(random_state=self._seed)` (was hardcoded `42` literal).
  - **Without these layers patched**, the CV would only measure `train_test_split` variance — KMeans clusters + KNN OOF folds + quantile boundaries would stay frozen across seeds and dramatically understate true noise.
  - **Backward-compat**: every kwarg defaults to `RANDOM_STATE` (=42). Existing single-seed runs (Runs 4, 9, 10) reproduce bit-identical-within-±5e-4 MAPE.

Re-runs detect the checkpoint and skip already-completed pairs unless `--fresh` is passed. - **Stage B.3 — paired noise-band decision rule**:
  - Compute `diffs = [blend_seed_i.mape − xgb_seed_i.mape for i in {42,43,44,45,46}]`.
  - `**mean(diffs) < 0` AND `|mean(diffs)| > std(diffs)`** → blend's lift survives the paired noise band → keep `blend_v1` as the udi/* champion.
  - `**mean(diffs) >= 0` AND `mean(diffs) > std(diffs)`** → xgboost wins outside noise band → recommend `xgboost_v3` for serving (already the simpler model).
  - **Otherwise (diff inside the band)** → recommend `xgboost_v3` for serving (one fewer moving part; blend's complexity isn't earning its keep).
  - **Why paired (not independent-std)**: `blend_v1` *contains* `xgboost_v3` internally — they share both the same per-seed split AND ~half the model variance (the xgboost sub-model is identical between the two runs at any given seed). An independent-std comparison would double-count noise. Same approach moses's `cv_validate.py` already uses for LightGBM/CatBoost.
